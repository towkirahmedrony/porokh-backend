# Phase 1 — Admission database foundation

**Status:** migration prepared for review; not executed or applied.
**Target project inspected:** ParaPoth / Supabase project `pbswsbfcmztmbcqnuqny` (ap-south-1), schema read 2026-10-30.
**Migration:** `supabase/migrations/20261030102000_admission_database_foundation.sql`

This phase adds the relational foundation only. It does not add admission authoring APIs, admin screens, student queries, question import paths, or question/unit fields. That work is Phase 2 and has not begun.

## Relationship diagram

```text
public.institutions (university)
        1
        |
        | institution_id (UUID FK, ON DELETE RESTRICT)
        |
        *
public.admission_units
        1
        |
        | exam_papers.admission_unit_id (nullable UUID FK, ON DELETE RESTRICT)
        |
        *
public.exam_papers (id is TEXT)
        1
        |
        | exam_paper_questions.exam_id (existing FK; unchanged)
        |
        *
public.exam_paper_questions
        *
        |
        | exam_paper_questions.question_id (existing FK; unchanged)
        |
        1
public.questions
```

The existing `exam_paper_questions` table is not modified. No `university_id` or unit column is added to `questions`; university is resolved through `admission_units.institution_id` for unit-linked papers. Existing or unitless papers remain valid with `admission_unit_id IS NULL`.

## Live-schema facts used to design the migration

Read-only inspection confirmed:

- `institutions.id` is `uuid`, generated by `gen_random_uuid()`; names and `type` are required. `institutions` already has `is_active`, `display_order`, `created_at`, `updated_at`.
- `exam_papers.id` is `text`; `exam_papers.meta_data` is `jsonb`; existing papers currently have `{}` in the inspected project.
- `exam_papers` already uses the `update_updated_at_column()` trigger; `institutions` uses `public.set_updated_at()`. The migration uses the existing `set_updated_at()` function for units.
- The existing paper and exam-question relationship is retained. No existing rows are backfilled or rewritten.
- The existing `public.is_admin()` function is SECURITY DEFINER, checks an active admin/super-admin role and active profile, and is executable by `authenticated` / `service_role`. The new RLS management policy uses it.
- The connected database currently has no `admission_units` table and no `exam_papers.admission_unit_id` column.

These are facts about the single active project inspected, not a guarantee about other Supabase environments.

## Unit table and integrity rules

`public.admission_units` contains:

- UUID primary key.
- Required `institution_id` → `institutions.id` FK; update cascades, delete is restricted.
- Required Bangla name `name_bn`; optional `name_en` and description.
- Required `code`; blank/whitespace-only codes are rejected.
- Unique expression index on `(institution_id, lower(btrim(code)))`: codes differing only by case or surrounding whitespace cannot collide within the same institution; another institution may use that code.
- `is_active`, `display_order`, and non-null timestamps with defaults.
- An update trigger using the existing `public.set_updated_at()` function.

`exam_papers.admission_unit_id` is nullable, references the new table, and has a partial index for non-null values. The FK restricts deletion of a unit still referenced by a paper; deactivation is the safe normal operation. There is intentionally no new university FK on `exam_papers` because the parent university is available through the unit.

## Canonical metadata contract

The migration comments document this forward-looking `exam_papers.meta_data` contract without adding a restrictive JSON check or replacing existing JSON:

```json
{
  "exam_mode": "past_exam",
  "admission_session": "2025-2026",
  "admission_display": {
    "subtitle_bn": "পূর্ববর্তী ভর্তি পরীক্ষা",
    "subtitle_en": "Previous admission paper",
    "display_order": 1
  },
  "group": "science",
  "unit_slug": "ka",
  "year": 2025
}
```

`exam_mode` is one of `past_exam`, `subject_practice`, or `model_test`. `admission_session` is a string. `admission_display` is optional presentation-only metadata. This is a metadata contract, not a new relational unit representation. A newly linked paper should use `admission_unit_id` as the canonical unit identity. The sample retains `group`, `unit_slug`, and `year` as compatibility keys for the existing student adapter; do not delete or rename legacy keys during Phase 1.

The live project did not contain an admission paper or stored university/unit metadata to use as a real production row example. Existing student adapter tests demonstrate reader-supported key variants but are fixtures, not production data. The current admin/backend authoring API does not yet write `meta_data` or `admission_unit_id`; enabling it is Phase 2.

## RLS and privileges

The migration enables RLS on `admission_units` and defines:

- `SELECT` for `anon` and `authenticated` only when `is_active IS TRUE`, consistent with public directory/catalog data.
- A separate `FOR ALL` policy for `authenticated` using `public.is_admin()` in both `USING` and `WITH CHECK`; admins can manage active or inactive rows, students cannot mutate them.
- Explicit grants: catalog `SELECT` to `anon` / `authenticated`; `INSERT`/`UPDATE`/`DELETE` to `authenticated` subject to RLS; all privileges to server-only `service_role`. It revokes the default table privileges before granting the intended subset.

The service-role credential must remain server-only as in the existing backend. No client receives a service-role key or RLS bypass.

## Backward compatibility and safety

- `exam_papers.admission_unit_id` is nullable, so existing papers require no data backfill and remain valid.
- The migration does not drop or rename tables, columns, indexes, policies, or metadata keys.
- `exam_paper_questions`, question IDs/order, questions, HSC data, bookmarks, wrong answers and histories are untouched.
- Admission-unit codes can match across universities but not within one university.
- The migration uses `IF NOT EXISTS` for the table, column and indexes and checks before adding the FK. It is additive and has no destructive data statement.
- In-use units cannot be deleted; mark them inactive instead.
- The metadata comment records the canonical shape but no database constraint forces that shape; this avoids rejecting legacy JSON and keeps app validation for Phase 2.

## Validation checklist

**Verified without applying the migration:** actual parent/target ID types, existing timestamps and trigger helper, existing admin helper, absence of the target table/column, nullable-column compatibility by design, and no changes to the question-association table in the migration text.

**Encoded by migration constraints/policies, but not executed in a database because the migration was not applied:**

- Multiple units may share one institution; duplicate codes within that institution are rejected case-insensitively.
- Different institutions may reuse a unit code.
- An exam paper can reference an existing unit; an unknown unit is rejected by the FK.
- Existing exam papers may keep a null unit reference.
- Existing question assignments remain unaffected because the join table is unchanged.
- HSC papers and questions remain valid because no HSC data or question fields are changed.
- Active units are readable by students; only active admins/super-admins can manage rows through authenticated RLS.

No live writes, migration apply, reset, or production validation transaction were run. A local Supabase/Postgres runtime was not available in the audit sandbox. Run functional constraint/RLS tests against an isolated development project before approving production execution.

## Remaining limitations

- Student app/admin/backend do not yet select or author normalized units. The new schema alone does not make unit-linked papers browsable; that is Phase 2.
- Existing admission metadata is not backfilled into `admission_units`; the connected database had no admission papers to backfill.
- `exam_mode` / `admission_session` are documented but not constrained or consumed by this phase.
- Current legacy adapter compatibility reads JSON keys; it does not yet join `admission_units` through `admission_unit_id`.
- Runtime migration tests and policy tests remain unrun; do not interpret static review as applied-schema proof.
